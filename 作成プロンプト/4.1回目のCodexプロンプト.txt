十分な情報が集まりました。追加質問なしで実装仕様まで落とせます。

技術構成は **Django + Django Templates + Vanilla JavaScript + SQLite** とし、フロントエンドのビルド環境は不要にします。Djangoは安定性重視で **5.2 LTS系の最新パッチ版**を指定するのがよいでしょう。Django 5.2はLTSで、Python 3.10〜3.14をサポートしています。:chatgpt-content-reference{index="0"}

また、単なる「材料置換AI」ではなく、**材料変更による分量・水分・油脂・塩分・加熱時間・工程への影響まで連鎖的に再設計するRecipe Refiner**として仕様化しました。

そのままCodexに投入できるプロンプトです。

# 料理レシピ・リファインWebアプリを実装してください

Python / Djangoをバックエンド、HTML / CSS / Vanilla JavaScriptをフロントエンドとして、料理レシピをLLMでリファインするWebアプリケーションを新規構築してください。

このアプリは個人利用を目的とします。

React、Vue、TypeScriptなどのフロントエンドフレームワークは使用しないでください。

Dockerも使用しません。

Pythonのパッケージ管理には `uv` を使用してください。

---

# 1. アプリの目的

このアプリは、既存の料理レシピに対してユーザーが変更希望を入力し、その条件を考慮してLLMがレシピ全体を再設計するアプリです。

例えば元レシピとして、

```text
カレー 4人前

材料
玉ねぎ 2個
にんじん 1本
じゃがいも 2個
牛肉 300g
カレールー 4皿分
水 600ml

作り方
1. 野菜を切る
2. 牛肉を炒める
3. 野菜を加える
4. 水を加えて煮込む
5. カレールーを加える
```

というレシピがあり、ユーザーが、

```text
玉ねぎがありません。
牛肉を豚肉にしてください。
2人前にしてください。
少し辛さを抑えたいです。
```

と入力すると、単純に文字列置換するのではなく、

- 材料
- 分量
- 水分量
- 味付け
- 加熱時間
- 調理工程
- 使用する調理器具

などへの影響も考慮して、新しいレシピを生成してください。

# 7. Recipe Refinerの最重要思想

このアプリで最も重要な部分です。

LLMには「文字列置換」をさせるのではなく、

**料理として成立するようにレシピ全体を再設計**

させてください。

例えば、

```text
生クリーム → 牛乳
```

という要求があった場合、

単純に、

```text
生クリーム100ml → 牛乳100ml
```

と置換してはいけません。

必要なら、

- 牛乳の量
- 油脂量
- 水分量
- とろみ
- 加熱方法
- 加熱時間

などを調整してください。

同様に、

```text
牛肉 → 豚肉
```

なら、

必要に応じて、

- 火入れ
- 調理時間
- 油
- 味付け

なども見直してください。

# 8. 元レシピ尊重

リファインでは、元レシピを可能な限り維持してください。

ユーザーから指示されていない部分を不用意に変更してはいけません。

基本ルールを、

```text
必要最小限の変更で、料理として成立させる
```

としてください。

つまり、

```text
忠実度：高
創作性：低
```

を基本方針としてください。

---

# 9. 人数変更

人数変更が要求された場合は、材料量を適切に調整してください。

例えば、

```text
4人前 → 2人前
```

なら基本的には半量ですが、

すべてを機械的に0.5倍するだけではなく、

- 塩
- 香辛料
- 油
- 水
- 調味料

などは料理として自然な分量に丸めてください。

例えば、

```text
卵 0.5個
```

など不自然な表現になった場合は、料理として妥当な方法を考えてください。

---

# 10. 変更できない場合

ユーザー要求によって料理として成立しにくくなる場合、

LLMが勝手に別料理へ変更してはいけません。

例えば、

```text
小麦粉なしでパンを作りたい
```

など、元レシピの本質を大きく変更する必要がある場合です。

この場合は、

```text
needs_confirmation
```

状態を返してください。

画面には、

```text
この変更では元のレシピをそのまま維持することが難しい可能性があります。
```

のようなメッセージと、

- 問題となる理由
- 必要になる大きな変更
- 代替案

を表示してください。

そのうえで、

```text
この条件で続行
```

と、

```text
変更内容を修正
```

を選択できるようにしてください。

「この条件で続行」を選択した場合のみ、再度LLMへ送信してリファインしてください。

# 15. LLM出力形式

LLMから自由文章だけを返させないでください。

JSONとして扱える構造化出力を要求してください。

概念的には以下の形式です。

```json
{
  "status": "ok",
  "recipe": {
    "title": "料理名",
    "servings": "2人前",
    "ingredients": [
      {
        "name": "豚肉",
        "amount": "150",
        "unit": "g",
        "note": ""
      }
    ],
    "steps": [
      {
        "order": 1,
        "instruction": "..."
      }
    ],
    "estimated_time_minutes": 30,
    "notes": []
  },
  "changes": [
    {
      "type": "ingredient_substitution",
      "before": "牛肉",
      "after": "豚肉",
      "reason": "ユーザーの指定"
    }
  ],
  "assumptions": [],
  "warnings": []
}
```

確認が必要な場合は、

```json
{
  "status": "needs_confirmation",
  "confirmation": {
    "message": "...",
    "concerns": [
      "..."
    ],
    "alternatives": [
      "..."
    ]
  }
}
```

のようにしてください。

厳密なschemaは実装時に改善して構いません。

# 17. LLM System Prompt

LLMへ与えるsystem promptは別ファイルまたは専用モジュールで管理してください。

以下の思想を必ず含めてください。

```text
あなたは料理レシピを編集・再設計する専門アシスタントです。

ユーザーから、
1. 元の料理レシピ
2. 変更希望
が与えられます。

元レシピを可能な限り維持しながら、変更希望を満たすようにレシピ全体を調整してください。

単純な文字列置換をしてはいけません。

材料を変更した場合は、その変更による以下への影響を検討してください。

- 分量
- 水分量
- 油脂量
- 塩分
- 甘味
- 酸味
- 香辛料
- とろみ
- 加熱温度
- 加熱時間
- 調理順序
- 使用する調理器具

変更する必要がない項目は元レシピを維持してください。

ユーザーが指定していない変更を不必要に追加してはいけません。

料理として成立しない、または元レシピから非常に大きな変更が必要になる場合は、勝手に変更せず needs_confirmation を返してください。

材料や分量に曖昧な点がある場合は、推測した内容を assumptions に明記してください。

食品アレルギーについて、完全な安全性を保証する表現をしてはいけません。

カロリーについて正確な栄養計算データがない場合、正確な数値として断定してはいけません。

指定されたJSON schemaだけを出力してください。
```

これをベースに、実用性が高くなるよう改善してください。

# 最重要要件

このアプリの本質は、

```text
元レシピの文章を書き換えること
```

ではありません。

**ユーザーが指定した変更によって生じる料理上の影響を考え、元レシピを可能な限り維持しながら、料理として成立する新しいレシピに再構成すること**

です。

例えば材料を1つ変えた場合でも、

```text
材料変更
   ↓
水分量への影響
   ↓
味付けへの影響
   ↓
加熱方法への影響
   ↓
加熱時間への影響
```

という連鎖をLLMに考慮させてください。

一方で変更の必要がない箇所は元レシピを維持してください。

**「最小限の変更で最大限自然なレシピにする」**

ことをRecipe Refinerの基本思想としてください。

この仕様で特に重要なのは、**Revisionを親子関係で保存する設計**です。これにより単なる履歴ではなく、

`原本 → 豚肉版 → 2人前版 → 辛口版`

という「レシピの派生系統」を持てます。将来的には特定Revisionから枝分かれさせて、**「A案：豆乳」「B案：牛乳」「C案：オーツミルク」**のようなレシピのブランチ比較まで発展させられます。

なお、OpenAI公式Python SDKではResponses APIが現在の主要インターフェースで、vLLMもOpenAI互換のResponses APIとChat Completions APIを提供しています。今回のProvider抽象化はこの両方を無理なく扱える構成にしています。:chatgpt-content-reference{index="1"}
