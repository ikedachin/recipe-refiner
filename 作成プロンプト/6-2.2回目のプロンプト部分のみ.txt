# 料理レシピ・リファインWebアプリを実装してください

Python / Djangoをバックエンド、HTML / CSS / Vanilla JavaScriptをフロントエンドとして、料理レシピをLLMでリファインするWebアプリケーションを新規構築してください。

このアプリは個人利用を目的とします。

React、Vue、TypeScriptなどのフロントエンドフレームワークは使用しないでください。

Dockerも使用しません。

Pythonのパッケージ管理には `uv` を使用してください。

---

# 1. アプリの目的

このアプリは、既存の料理レシピに対してユーザーが変更希望を入力し、その条件を考慮してLLMがレシピ全体を再設計するアプリです。

例えば元レシピとして、

```text
カレー 4人前

材料
玉ねぎ 2個
にんじん 1本
じゃがいも 2個
牛肉 300g
カレールー 4皿分
水 600ml

作り方
1. 野菜を切る
2. 牛肉を炒める
3. 野菜を加える
4. 水を加えて煮込む
5. カレールーを加える
```

というレシピがあり、ユーザーが、

```text
玉ねぎがありません。
牛肉を豚肉にしてください。
2人前にしてください。
少し辛さを抑えたいです。
```

と入力すると、単純に文字列置換するのではなく、

- 材料
- 分量
- 水分量
- 油脂量
- 味付け
- 加熱時間
- 調理工程
- 使用する調理器具

などへの影響も考慮して、新しいレシピを生成してください。

# 2. 技術構成

以下を基本構成としてください。

## Backend

- Python 3.12以上
- Django
- Django Templates
- SQLite
- OpenAI Python SDK
- Pydantic
- PyYAML
- python-dotenv等による環境変数管理

DjangoについてはDjango 5.2 LTS系を基本としてください。

## Frontend

- HTML
- CSS
- Vanilla JavaScript

以下は使用しないでください。

- React
- Next.js
- Vue
- Svelte
- TypeScript

Node.jsやnpmを必須にするフロントエンドビルド工程も作らないでください。

## Package management

Python依存関係は `uv` で管理してください。

以下で環境構築できる状態にしてください。

```bash
uv sync
```

実行についても、

```bash
uv run python manage.py migrate
uv run python manage.py runserver
```

で起動できるようにしてください。

# 5. 元レシピ入力

元レシピは自由形式のtextareaとしてください。

Webサイトや料理本などから、ユーザー自身がレシピ文章をコピーして貼り付けます。

初期バージョンでは以下は不要です。

- URL取得
- Webスクレイピング
- PDF読み込み
- OCR
- 画像入力
- ファイルアップロード

また、LLM呼び出し前に元レシピを別処理で構造化する必要もありません。

入力された文章を基本的にそのままLLMへ渡してください。

# 6. 変更希望入力

右側には自由形式のtextareaを設置してください。

専用フォームや変更項目ごとの入力欄は作らないでください。

例えば、

```text
玉ねぎがありません。
牛肉を豚肉に変更してください。
4人分を2人分にしてください。
フライパンだけで作れるようにしてください。
辛さを少し抑えてください。
```

のように自然言語で入力します。

想定される変更内容には以下があります。

- 材料不足
- 材料置換
- 人数変更
- 分量変更
- 味付け変更
- 調理時間変更
- 調理器具変更
- カロリーに関する変更
- アレルギーに関する変更
- ベジタリアン対応

ただしUIではこれらを個別フォームにしないでください。

# 7. Recipe Refinerの最重要思想

このアプリで最も重要な部分です。

LLMには単純な文字列置換をさせるのではなく、

**料理として成立するようにレシピ全体を再設計**

させてください。

例えば、

```text
生クリーム → 牛乳
```

という要求があった場合、

単純に、

```text
生クリーム100ml → 牛乳100ml
```

と置換してはいけません。

必要に応じて、

- 牛乳の量
- 油脂量
- 水分量
- とろみ
- 味付け
- 加熱方法
- 加熱時間

などを調整してください。

同様に、

```text
牛肉 → 豚肉
```

なら、

必要に応じて、

- 火入れ
- 加熱時間
- 油
- 調味料

なども見直してください。

---

# 8. 元レシピ尊重

リファインでは、元レシピを可能な限り維持してください。

ユーザーから指示されていない部分を不用意に変更してはいけません。

基本ルールは、

```text
必要最小限の変更で、料理として成立させる
```

です。

基本方針は、

```text
忠実度：高
創作性：低
```

としてください。

---

# 9. 人数変更

人数変更が要求された場合は、材料量を適切に調整してください。

例えば、

```text
4人前 → 2人前
```

なら基本的には半量ですが、

すべてを機械的に0.5倍するだけではなく、

- 塩
- 香辛料
- 油
- 水
- 調味料

などは料理として自然な分量へ調整してください。

例えば、

```text
卵 0.5個
```

など不自然な結果になる場合は、料理として実行可能な表現や方法を考えてください。

---

# 10. 変更が大きすぎる場合

ユーザー要求によって料理として成立しにくくなる場合や、元レシピの本質を大きく変更する必要がある場合、LLMが勝手に別料理へ変更してはいけません。

例えば、

```text
小麦粉を使わず、他の粉類も使わずにパンを作りたい
```

などです。

この場合は、

```text
needs_confirmation
```

状態を返してください。

画面には、

```text
この変更では元のレシピを維持することが難しい可能性があります。
```

のようなメッセージと、

- 問題となる理由
- 必要になる大きな変更
- 代替案

を表示してください。

そのうえで、

```text
この条件で続行
```

と、

```text
変更内容を修正
```

を選択できるようにしてください。

「この条件で続行」を選択した場合のみ、再度LLMへ送信してリファインしてください。

# 11. LLM Provider設計

このアプリでは以下を利用可能にしてください。

1. OpenAI API
2. OpenAI互換のローカルLLM

ローカルLLMとしては主にvLLMを想定します。

重要な要件として、

**OpenAI APIとローカルLLMの切り替えはYAML設定ファイルで行う**

ようにしてください。

Provider依存コードをViewへ直接書かないでください。

以下のような構造を基本としてください。

```text
recipes/
    services/
        llm/
            base.py
            openai_provider.py
            openai_compatible_provider.py
            factory.py
            config.py
            prompts.py
            schemas.py
```

共通インターフェースとして、例えば、

```python
class LLMProvider:
    def refine_recipe(...):
        ...
```

のような抽象化を行ってください。

# 12. YAMLによるLLM設定

LLM関連の非機密設定はYAMLファイルへ集約してください。

例えば、

```text
settings/
    llm.yaml
```

を作成してください。

設定例は以下です。

```yaml
provider: openai

openai:
  model: gpt-5.6
  api_style: responses

local:
  base_url: http://localhost:8000/v1
  model: Qwen3.8-27B-NVFP4
  api_style: chat_completions

generation:
  timeout_seconds: 120
  temperature: 0.2

retry:
  invalid_response_max_retries: 1
```

`provider` は、

```yaml
provider: openai
```

または、

```yaml
provider: local
```

を指定できるようにしてください。

つまり、

```yaml
provider: openai
```

ならOpenAI API、

```yaml
provider: local
```

ならvLLM等のローカルLLMを使用します。

---

# 13. YAMLをSingle Source of Truthにする

LLM Providerについては、

```text
settings/llm.yaml
```

を設定のSingle Source of Truthにしてください。

Provider切り替えを、

- Pythonソースコード
- Django View
- JavaScript
- HTML
- `.env`

へハードコードしてはいけません。

必ずYAML設定を読み取ってProviderを決定してください。

ブラウザ上からProviderを切り替える機能は初期バージョンでは不要です。

Providerを変更したい場合は、

```yaml
provider: openai
```

を、

```yaml
provider: local
```

へ変更してDjangoを再起動する運用で構いません。

---

# 14. YAML設定ローダー

YAMLを直接各ファイルから読み込まないでください。

設定読み込み処理を1か所に集約してください。

例えば、

```text
recipes/services/llm/config.py
```

を作成してください。

概念的には、

```python
@dataclass(frozen=True)
class LLMConfig:
    provider: str
    ...
```

などの型付き設定オブジェクトへ変換してください。

またはPydanticによる設定schemaを使用しても構いません。

以下を検証してください。

- `provider` が `openai` / `local` のどちらか
- modelが設定されている
- localの場合はbase_urlが設定されている
- api_styleがサポート対象である
- timeoutが正の値
- temperatureの値が妥当

不正な設定の場合は、起動時または最初のLLM利用時に分かりやすいエラーを出してください。

---

# 15. YAMLと秘密情報を分離する

APIキーなどの秘密情報をYAMLへ保存してはいけません。

YAMLには非機密設定だけを保存してください。

秘密情報は `.env` に保存します。

例えば、

```env
DJANGO_SECRET_KEY=change-me
DJANGO_DEBUG=True

OPENAI_API_KEY=

LOCAL_LLM_API_KEY=dummy
```

としてください。

つまり役割を以下のように明確に分離してください。

```text
settings/llm.yaml
    ↓
Provider
モデル名
base_url
api_style
timeout
generation設定

.env
    ↓
API key
Django SECRET_KEY
その他secret
```


OpenAI固有の処理はProvider内部へ閉じ込めてください。

# 18. LLM Factory

YAML設定に応じてProviderを生成するFactoryを作成してください。

概念的には、

```python
def create_llm_provider(config: LLMConfig) -> LLMProvider:
    if config.provider == "openai":
        return OpenAIProvider(...)
    if config.provider == "local":
        return OpenAICompatibleProvider(...)
```

のような役割です。

View側では、

```python
if provider == ...
```

という分岐を書かないでください。

# 20. LLM出力形式

LLMから自由文章だけを返させないでください。

JSONとして扱える構造化された出力を要求してください。

概念的には以下です。

```json
{
  "status": "ok",
  "recipe": {
    "title": "料理名",
    "servings": "2人前",
    "ingredients": [
      {
        "name": "豚肉",
        "amount": "150",
        "unit": "g",
        "note": ""
      }
    ],
    "steps": [
      {
        "order": 1,
        "instruction": "..."
      }
    ],
    "estimated_time_minutes": 30,
    "notes": []
  },
  "changes": [
    {
      "type": "ingredient_substitution",
      "before": "牛肉",
      "after": "豚肉",
      "reason": "ユーザーの指定"
    }
  ],
  "assumptions": [],
  "warnings": []
}
```

確認が必要な場合は、

```json
{
  "status": "needs_confirmation",
  "confirmation": {
    "message": "...",
    "concerns": [
      "..."
    ],
    "alternatives": [
      "..."
    ]
  }
}
```

のようにしてください。

厳密なschemaは実装時に改善して構いません。

---

# 21. Pydantic validation

LLM出力は必ずPydanticで検証してください。

以下に相当するモデルを作成してください。

```text
Ingredient
RecipeStep
RefinedRecipe
RecipeChange
Confirmation
RecipeRefineResponse
```

JSONとして解析できない場合やschema validationに失敗した場合は、500エラーをそのままユーザーへ表示してはいけません。

YAMLで、

```yaml
retry:
  invalid_response_max_retries: 1
```

などを設定できるようにしてください。

1回再生成しても失敗した場合は、

```text
レシピの生成結果を正しく解析できませんでした。
もう一度お試しください。
```

などのユーザー向けエラーとして扱ってください。

# 22. LLM System Prompt

LLMへ与えるsystem promptは専用モジュールで管理してください。

View内に巨大なpromptを書いてはいけません。

以下の思想を必ず含めてください。

```text
あなたは料理レシピを編集・再設計する専門アシスタントです。

ユーザーから、
1. 元の料理レシピ
2. 変更希望
が与えられます。

元レシピを可能な限り維持しながら、変更希望を満たすようにレシピ全体を調整してください。

単純な文字列置換をしてはいけません。

材料を変更した場合は、その変更による以下への影響を検討してください。

- 分量
- 水分量
- 油脂量
- 塩分
- 甘味
- 酸味
- 香辛料
- とろみ
- 加熱温度
- 加熱時間
- 調理順序
- 使用する調理器具

変更する必要がない項目は元レシピを維持してください。

ユーザーが指定していない変更を不必要に追加してはいけません。

料理として成立しない、または元レシピから非常に大きな変更が必要になる場合は、勝手に変更せず needs_confirmation を返してください。

材料や分量に曖昧な点がある場合は、推測した内容を assumptions に明記してください。

食品アレルギーについて、完全な安全性を保証する表現をしてはいけません。

カロリーについて正確な栄養計算データがない場合、正確な数値として断定してはいけません。

指定されたJSON schemaだけを出力してください。
```

これをベースに実用性が高くなるよう改善してください。

# 最重要要件

このアプリの本質は、

```text
元レシピの文章を書き換えること
```

ではありません。

**ユーザーが指定した変更によって生じる料理上の影響を考え、元レシピを可能な限り維持しながら、料理として成立する新しいレシピへ再構成すること**

です。

例えば材料を1つ変更した場合でも、

```text
材料変更
   ↓
水分量への影響
   ↓
味付けへの影響
   ↓
加熱方法への影響
   ↓
加熱時間への影響
```

という連鎖をLLMに考慮させてください。

一方で変更の必要がない箇所は元レシピを維持してください。

**「最小限の変更で最大限自然なレシピにする」**

ことをRecipe Refinerの基本思想としてください。

また、LLM設定については、

**「非機密設定はYAML、秘密情報は.env」**

という責務分離を必ず守ってください。

最終的に、

```yaml
provider: openai
```

と、

```yaml
provider: local
```

を書き換えるだけでLLM Providerを切り替えられる状態にしてください。
